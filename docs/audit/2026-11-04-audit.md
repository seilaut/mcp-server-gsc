## (b) Bugs, config and drift

**Code bugs (V by reading; none were exercised against Google).**

- **F7.** `sitemaps.submit` needs the write scope `https://www.googleapis.com/auth/webmasters`. I checked Google's public discovery document (no credentials sent): `https://searchconsole.googleapis.com/$discovery/rest?version=v1`, revision 20261103, lists exactly that scope. The code only asks for `webmasters.readonly` (`src/search-console.ts:26,31`), so `submit_sitemap` can never succeed. After the 403, `handlePermissionError` retries with a rewritten `siteUrl`, which is a second call that also fails. This needs a decision from Diego (see the open questions).
- **F8.** `normalizeUrl` (`src/search-console.ts:52-58`) mishandles every input shape:
  - `sc-domain:example.com` parses as protocol `sc-domain:` and becomes `https://sc-domain:example.com`.
  - A bare host makes `new URL()` throw a TypeError, which hides the original error.
  - `https://www.example.com/` becomes `sc-domain:www.example.com`, keeping the `www.`.

  `handlePermissionError` (`:60-72`) runs this fallback on **any** error whose message contains "permission". So a URL-prefix query can silently return a domain property's numbers, which cover all subdomains and protocols, with nothing in the answer saying so. Upstream PR #9 (closed, never merged) lists a fix for the crash.
- **F16.** `detect_quick_wins` calls `searchAnalytics` (`src/server.ts:169`) and then `enhancedSearchAnalytics` (`:193`), which calls it again (`src/search-console.ts:123`). That is two 25,000-row queries per call. The tool accepts `estimatedClickValue` and `conversionRate` (`src/schemas.ts:101-102`) and never uses them. `regexFilter` sits in the base schema (`:42`) but the `search_analytics` branch ignores it. The enhanced branch applies it only when `dimensions` includes `query` (`src/search-console.ts:108`).
- **F17.**
  - `GetSitemapSchema.feedpath` and `ListSitemapsSchema.siteUrl` are optional (`src/schemas.ts:60-82`), but the API needs them. The fallback then calls `normalizeUrl(requestBody.siteUrl!)` with `undefined` (`src/search-console.ts:215,227`).
  - `list_sites` throws "Arguments are required" if a client leaves out `arguments` (`src/server.ts:84-86`). The MCP spec makes `arguments` optional.
  - Dates are unchecked strings (`src/schemas.ts:12-13,95-96`), and `rowLimit` accepts non-integers (`:32`).
- **F18.** `capabilities` declares `resources: {}` and `prompts: {}` (`src/server.ts:27-31`) but registers no handler for them. I infer that `resources/list` returns "method not found". A new `SearchConsoleService`, and so a new `GoogleAuth` and a new token, is created on every tool call (`src/server.ts:88`).

## (c) Security

**Secrets in code and history.** Clean, see the top section. No key-like files are present.

**How Google credentials load (V by reading).**

- **stdio:** `GOOGLE_APPLICATION_CREDENTIALS` must be set (`src/index.ts:7-11`). `SearchConsoleService` treats a value starting with `{` as inline JSON and anything else as a key-file path (`src/search-console.ts:15-34`). The scope is read-only, which is good least privilege.
- **Worker:** the whole service-account JSON comes from the `GOOGLE_CREDENTIALS` secret (`src/remote.ts:32-36`).
- **Leak paths:**
  - Errors are logged with `console.error(error)` (`src/server.ts:359`). gaxios 7.3.1 (`build/cjs/src/gaxios.js:413-415`, `common.js:234-297`, read from unpkg) applies its `defaultErrorRedactor` unless that is explicitly disabled. It redacts `Authorization` and `Authentication` headers, the JWT `assertion`, `grant_type` and anything containing "secret". So a token leak through logs is unlikely (F19).
  - Credentials only come from the operator (env or secret), never from MCP clients. The google-auth-library risk with untrusted `external_account` configs therefore does not apply.
  - `.dev.vars` is not git-ignored (F15).

**Auth on the remote Worker endpoint (F5, V by reading).**

- `app.use('/mcp', …)` calls `bearerAuth` only `if (token)` (`src/remote.ts:20-27`). With `MCP_API_TOKEN` unset or empty, `/mcp` is open to anyone who knows the `workers.dev` URL. They could list every property the service account can see (`list_sites`) and read all of its search data.
- CORS defaults to `*` (`:16`). There is no rate limiting, even though `@hono/mcp` peers `hono-rate-limiter`.
- Each request builds a new server and auth client (`:36`), and the first tool call in it does a Google token exchange. That multiplies cost, and Google API quota is exhausted faster if the URL or token leaks.
- The route and middleware paths match exactly (`/mcp`), and preflight is handled by CORS before auth. I found no path-variant bypass (I, from Hono's default strict, case-sensitive routing).
- **Deployment status: unknown.** The repo has no `account_id`, routes or CI, and I made no Cloudflare calls. This finding is latent if the Worker is not deployed and critical if it is deployed without the secret. The plan has no task that fixes it.

**Input validation and SSRF (F17).** zod parses every tool's arguments. The gaps are listed in (b). **No SSRF:** every outbound request goes to Google API hosts that googleapis fixes in advance. The user-supplied URLs (`siteUrl`, `inspectionUrl`, `feedpath`, `sitemapIndex`) travel as API parameters, and the server itself never fetches them (I: I did not inspect googleapis-common's URL templating).
